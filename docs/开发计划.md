## 三、里程碑与自检规则

1. 每两周一个肉眼可见验收点（上表每行"验收标准"）
2. 每周日 15 分钟复盘：本周验收达成了吗？卡点是什么？
3. 连续两周未达验收 → 砍本周最不重要的功能，保 MVP 主线
4. 需求变更先写决策记录，再评估影响（表/实体/DAO/页面）
5. 铁律：改代码 → 停 Tomcat → `mvn clean package` → `cargo:run`

## 四、v2 路线图（大学教学模拟）

- 最小可玩：学期推进 → 课程自动合法导入（培养方案自动开课 + 自动排课无冲突 + 学生自动选课）
- 架构：JSON API 层（/api/*，复用 service/dao）→ 游戏界面客户端（**已定：Unity2D**，2026-09-30 决策）
- 分工：模拟引擎（tick 循环 + 个体行为规则）放 Java 后端 service 层；Unity 负责画面渲染与上帝干预（参照 WorldBox 分工）
- 衔接：Unity C# UnityWebRequest 调 /api/*（非浏览器无 CORS 限制）；后端需补 JSON 序列化（Jackson/Gson）
- v1 已预留：专业表、week_type 列、service 层骨架、checkConflicts 可复用接口

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 拖延/完美主义（无截止日期） | 周里程碑自检，功能"先能用再好看" |
| 冲突检测难度 | 规则拆成三个"且"条件逐个实现，允许溢出到第 5 周 |
| 多表写操作一致性 | 先删后插约定 + 外键保护兜底 +（进阶）事务 |
| 需求再变更 | 决策记录先行，变更前评估影响面 |
