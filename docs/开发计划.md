## 三、里程碑与自检规则

1. 每两周一个肉眼可见验收点（上表每行"验收标准"）
2. 每周日 15 分钟复盘：本周验收达成了吗？卡点是什么？
3. 连续两周未达验收 → 砍本周最不重要的功能，保 MVP 主线
4. 需求变更先写决策记录，再评估影响（表/实体/DAO/页面）
5. 铁律：改代码 → 停 Tomcat → `mvn clean package` → `cargo:run`

## 四、v2 路线图（大学教学模拟）

> 总原则：**先让世界在网页控制台活起来，再给世界做相机（Unity）**。
> 模拟引擎全部放 Java service 层，纯 Java + main 测试驱动（第 4 周 checkConflicts 工作方式的放大版）。
> 技术决策（2026-09-30 已定）：界面 Unity2D；分工参照 WorldBox——引擎在后端跑，Unity 只渲染与干预。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 拖延/完美主义（无截止日期） | 周里程碑自检，功能"先能用再好看" |
| 冲突检测难度 | 规则拆成三个"且"条件逐个实现，允许溢出到第 5 周 |
| 多表写操作一致性 | 先删后插约定 + 外键保护兜底 +（进阶）事务 |
| 需求再变更 | 决策记录先行，变更前评估影响面 |
| C#/Unity 学习曲线（v2 新） | 第 16 周专设学习周；Unity 界面"方块+文字"起步，不追求美术 |
| 模拟引擎调试难（v2 新） | 纯 Java + main 测试驱动；先网页控制台跑通再上 Unity；tick 可单步 |
| 涌现效果不可控（v2 新） | 先接受"跑起来就有波动"；规则参数（精力阈值等）集中常量，便于调参 |
| v2 范围蔓延（v2 新） | 严守最小可玩（1 专业×20 学生）；新玩法进决策记录排队 |
